# Як порахувати σ_daily з реальної tickHistory (CSV)

Цей документ — продовження `range_width_risk_math.md`. Там `σ_daily` була
плейсхолдером (`0.0083`). Тут розписано, звідки взяти РЕАЛЬНЕ число з твого
власного `tickHistory` CSV, крок за кроком, з поясненням, чому саме так.

Файл, на якому я показую розрахунок (реальні дані твого пулу на Base,
239 днів історії, крок опитування ~5 хв):

```
Timestamp|int64,Tick|int64
1765954800,76364
1765955100,76384
...
```

---

## Крок 0 — гігієна даних (це НЕ формальність, дані виявили реальні проблеми)

Перш ніж рахувати волатильність, дані треба привести до ладу. Я перевірив цей
конкретний файл і ось що знайшов:

1. **Дублікати таймстемпів.** З 76 007 рядків після дедуплікації (той самий
   `timestamp` кілька разів — залишаємо останній запис) лишилось 67 591. Тобто
   ~11% рядків були "шумом" від повторних записів.
2. **Розриви (простої бота / RPC).** Номінальний крок опитування — 5 хвилин
   (`300` секунд — це найчастіше значення різниці між сусідніми таймстемпами).
   Але знайшлось **28 розривів довше 1 години**, сумарно ~19 днів простою з 239
   (~8% усього періоду). Найбільший розрив — 86 годин.

**Чому це важливо:** якщо просто взяти "тік до розриву" і "тік після розриву"
і порахувати це як звичайний приріст за короткий інтервал — ми або
драматично недооцінимо волатильність (бо не бачили, що ціна робила всередині
розриву — могла піти туди-сюди і повернутись), або якщо там був різкий
стрибок, припишемо його як один "миттєвий" рух, хоча насправді він розтягнутий
у часі. Правильне рішення — **виключити з розрахунку інтервали, довші за
розумний поріг** (я взяв 1 годину = 12x номінальний крок), тобто розбити ряд
на "чисті" безперервні сегменти і рахувати статистику лише всередині них.

## Крок 1 — тік у логарифм ціни

Той самий крок, що й раніше:

```
logPrice = tick * ln(1.0001)
```

---

## Крок 2 — реалізована варіація (realized variance)

Це стандартний і найбільш надійний спосіб оцінити волатильність, коли дані
надходять НЕРІВНОМІРНО (як тут — крок то 5 хв, то 10 хв, то розрив на годину).
Ідея (той самий підхід, що використовують у high-frequency finance для
"realized volatility"):

Для кожної пари сусідніх точок (усередині одного "чистого" сегмента, без
розривів) рахуємо:

```
r_i  = logPrice_i − logPrice_{i-1}         (лог-дохідність за цей крок)
Δt_i = (timestamp_i − timestamp_{i-1}) / 86400     (тривалість кроку в днях)
```

Далі підсумовуємо по ВСІХ парах у ВСІХ сегментах:

```
RV        = Σ r_i²              (сума квадратів приростів = "реалізована варіація")
totalTime = Σ Δt_i              (сумарний "чистий" час у днях)
```

**Чому сума квадратів приростів взагалі щось означає?** Це властивість
броунівського руху (тієї самої моделі з попереднього документа): сума квадратів
приростів за малі кроки збігається до накопиченої дисперсії процесу за весь
період — незалежно від того, наскільки нерівномірно розставлені точки
вимірювання. Тому цей метод коректно працює навіть з "рваним" рядом даних, на
відміну від наївного "просто візьми stdev()" — там нерівномірність кроків
спотворила б результат.

## Крок 3 — з реалізованої варіації в σ_daily

Якщо процес — броунівський рух з денною волатильністю `σ`, то `E[RV] = σ² × totalTime`.
Звідси:

```
σ_daily = √(RV / totalTime)
```

**Результат на реальних даних цього файлу:**

```
n інтервалів використано: 67 562  (28 розривів виключено)
totalTime = 220.1 днів (з 239.4 номінальних — різниця це і є виключені розриви)
σ_daily ≈ 0.0481
```

Для порівняння — плейсхолдер, який ми використовували раніше, був `0.0083`,
тобто **майже в 6 разів менший** за реальний. Це наочно показує, чому
підставляти "число зі стелі" в формулу ризику небезпечно — з таким заниженим σ
розрахунок сильно переоцінював би, наскільки безпечно звужувати діапазон.

## Крок 4 — крос-перевірка іншим, "підручниковим" методом

Щоб не довіряти сліпо одній формулі, я порахував σ_daily ще одним, більш
класичним способом:

1. Ресемплити ряд на регулярну **годинну сітку** (для кожної години беремо
   останній записаний тік у цій годині; години без жодного запису — пропуск,
   із розривом ряду на сегменти, так само як у Кроці 0).
2. Порахувати звичайні лог-прирости між сусідніми годинними точками.
3. Взяти звичайне стандартне відхилення цих приростів — це `σ_hourly`.
4. Перевести в денну шкалу через **правило кореня з часу**
   (властивість броунівського руху: дисперсія лінійна за часом, тому стандартне
   відхилення масштабується як корінь з часу):
   ```
   σ_daily = σ_hourly × √24
   ```

**Результат:** `σ_daily ≈ 0.0499` — дуже близько до `0.0481` з Кроку 3
(розбіжність ~4%). Два незалежні методи збігаються — це хороший знак, що
оцінка стабільна, а не артефакт конкретного методу підрахунку.

## Крок 5 — чи стабільна волатильність у часі? (rolling-перевірка)

Волатильність кластеризується (спокійні періоди чергуються з бурхливими) — про
це вже йшлося як застереження в попередньому документі. Ось як це виглядає на
реальних даних, якщо порахувати σ_daily (методом реалізованої варіації) не по
всій історії, а по останніх N днях:

| Вікно         | σ_daily |
|---------------|---------|
| останні 239 днів (усе) | 0.0482 |
| останні 90 днів        | 0.0426 |
| останні 60 днів        | 0.0442 |
| останні 30 днів        | 0.0375 |
| останні 14 днів        | 0.0355 |
| останні 7 днів         | 0.0324 |

Видно чіткий тренд: **останні тижні волатильність помітно нижча** (~0.032-0.038),
ніж середнє за весь період (~0.048). Це не аномалія і не помилка розрахунку —
це саме той ефект нестаціонарності волатильності, про який попереджав
попередній документ. Практичний висновок: **яке вікно брати для σ, залежить
від того, для чого рахуєш**:

- Якщо хочеш оцінку "на найближчі дні/тижні" (тобто для рішення про поточну
  ширину діапазону прямо зараз) — розумніше брати σ з **недавнього** вікна
  (14-30 днів), а не з усієї 239-денної історії, бо старі бурхливі періоди
  вже, схоже, не репрезентативні для поточного режиму ринку.
- Якщо хочеш консервативну, "на всякий випадок" оцінку (з запасом на
  можливе повернення підвищеної волатильності) — бери довше вікно або навіть
  максимум із кількох вікон.

## Підсумок послідовності розрахунку (коротко)

1. Завантажити CSV, відсортувати за часом, прибрати дублікати таймстемпів.
2. Розбити ряд на безперервні сегменти, виключивши розриви довші за поріг
   (наприклад, 1 година).
3. Перевести кожен тік у логарифм ціни (`tick × ln(1.0001)`).
4. Порахувати приріст `r_i` і тривалість кроку `Δt_i` для кожної сусідньої
   пари точок УСЕРЕДИНІ одного сегмента.
5. `σ_daily = √(Σr_i² / Σ Δt_i)`.
6. (Опційно, для перевірки) повторити тим самим методом на регулярній
   годинній сітці зі stdev() і масштабуванням `×√24` — має дати близьке число.
7. Порахувати σ_daily на кількох вікнах (7/14/30/60/90 днів і весь період),
   щоб побачити, чи стабільна оцінка, і свідомо обрати, яке вікно
   використовувати далі в `range_width_calculator.go`.

Повний робочий код цього розрахунку — у файлі `sigma_calculator.go` поруч.
